# Porting the game to readable JavaScript (web/js/port)

The goal: the whole of Mario Tennis (GBC) as readable, exact JavaScript, running on the emulator's hardware
model (memory map, PPU, APU, timer, DMA) without its CPU. The match engine (web/js/engine) was the first part.
This guide is for everyone porting a part of the rest.

Source: the gerbiljames/mario-tennis-gbc-disasm (MIT), vendored at `third_party/mario-tennis-gbc-disasm`
(`src/`, symbols in `build/mariotennis.sym` after `make`). Keep its routine names (camelCase in JS); give the
ROM address of each routine in a comment, like `// ReadJoypad (00:02EB)`; credit the disassembly in each file's
header. Check behaviour against the ROM with the tests below, never only against the disassembly's comments.

## How a partly ported game runs (web/js/port/port.js)

`GamePort` runs the game as a coroutine (`program.main`, web/js/port/program.js). Anything not ported yet
is the ROM's own code, run on the emulator's CPU. The two meet in two ways:

- **Hooks.** A ported routine registers `[bank, addr, fn(P, cpu)]` in its module's `HOOKS`. When the ROM's
  code reaches `bank:addr` (bank is ignored below $4000), the port runs `fn` instead and returns as if by `ret`.
  The hook adapter reads its arguments from `cpu` (`cpu.a`, `cpu.b`, ..., `cpu.hl`, `cpu.de`, `cpu.bc`; flags
  in `cpu.f`: Z $80, C $10). It writes back **every register the ROM routine leaves changed**, and the flags it
  leaves when a caller tests them, because unported callers may use them. If the routine waits for frames, the
  hook returns a generator.
- **Calls into the ROM.** Ported code calls a routine that has no port yet with `P.callRom(bank, addr, regs)`.
  That returns the registers afterwards, and the routine must not wait. If it may wait, use
  `yield* P.runRom(bank, addr, regs)`. When the routine gets ported, replace the call with a direct JS call.

So port bottom-up, or top-down, or anything in between: the game keeps running and every routine is checked
in place.

## Writing a port

- One module per ROM source file or close group, in `web/js/port/<area>/<name>.js`. Areas: `home` (bank 0),
  `audio`, `text`, `menus`, `story`, `cutscenes`, `minigames`, `save`, `match` (the HUD/drawing banks
  around the engine). Each area has an `index.js` that gathers its modules' `HOOKS`; `program.js` gathers the
  areas. Add your module to your area's `index.js` only.
- Routines are plain functions with the port `P` first: `export function readJoypad(P) { ... }`. Use natural
  arguments and return values; the hook adapter maps them to registers.
- RAM by name: `P.V.name` reads and writes a variable (`wCurMapID` is `P.V.curMapID`, `hWramBank` is
  `P.V.wramBank`; 1-byte variables as u8, 2-byte ones as u16 little-endian). A variable in a switchable
  WRAM bank is read and written in its own bank, whatever is mapped. `P.A.name` is its address, and `P.B.name`
  its WRAM bank. Raw access, I/O registers and buffers go through `P.bus` (`u8/s8/u16/w8/w16/...`). Names come
  from web/js/port/fields.js, generated by tools/gen_port_fields.py.
- Banked WRAM: the ROM's `wram_bank` / `push_wram_bank` macros write both rSVBK ($FF70) and hWramBank ($FF96).
  Do the same with `P.wramBank(b)` and `P.withWramBank(b, fn)` (push ... pop); both are compared.
  `P.bus.bank` alone is rSVBK only. For a generator, save `P.V.wramBank`, set the bank with
  `P.wramBank(b)`, and restore it yourself.
- ROM data: `P.rom.u8(bank, addr)`, `u16`, `slice`, `lz` (decompressed). For code that indexes ROM through the
  bank mapped at the time, use `P.bus.romByte(P.mem.romBank, addr)`.
- Frames: a routine that waits is a generator, and `AdvanceFrame` is `yield* advanceFrame(P)` (home). Never
  busy-wait.
- Sounds: `rst $08 ; db id` is a call to the sound request routine with `id`. Port it as a call (home/audio).
- Far calls (`farcall X`, `rst $18 ; db idx, bank`): call the JS directly, or call the ROM with
  `P.callRom(bank, addr)` (the port maps the bank and sets hRomBank as FarCall does).
- Readable means: names for magic numbers where the disassembly has them (constants, flags), comments that say
  what and why, no register shuffling. It must stay exact: same RAM writes, same order where it matters (I/O),
  same results in all branches.

## Special routines

- **Interrupt handlers** (VBlankHandler 00:2749, LCDStatHandler, TimerHandler, SerialHandler) are hooked at
  their own address; the vectors at $40-$60 jump there. A handler's hook ends with `P.ime = true` (its `reti`).
  `jp SoftReset` from a handler is `throw new SoftResetSignal()` (port.js).
- **AdvanceFrame (00:2631)** as a generator: it starts with `yield* P.atAdvanceFrame()`, the point where the
  lockstep lines the port up with the ROM. Its wait is `do { yield "halt"; } while (!P.V.vBlankOccurred)`:
  each `yield "halt"` lets one frame of hardware pass, with the VBlank handler run at its start.
- **Timing.** Ported code takes no CPU time. Code that measures time (rLY polling, hPeakLY, DIV) gives other
  values. Keep reading the hardware exactly as the ROM does; the tests know which differences come from timing.

## Testing (both must pass before a part counts as ported)

1. **Routine tests.** Run `node web/tests/port_routines.mjs [filter]`. Entries live in
   `web/tests/port/routines_<area>.mjs`. Each entry calls the routine at its ROM address on the core (the ROM)
   and on a GamePort (your hook), from whole-machine states of recorded play. It then compares all RAM, VRAM,
   OAM, HRAM, SRAM, palettes, LCD registers and the listed result registers.
   - Entry shape: `{ name, bank, addr, out: ["a","hl",...], regs(state), prep(mem, state), when(state), wram }`.
   - Use `prep` to force rare branches.
   - Only routines that do not wait can be tested this way.
2. **Lockstep.** Run `node web/tests/port_lockstep.mjs [rec.mtrec]` with recordings from `out/engine/`.
   - It plays a recording on the ROM and on the port, lined up on AdvanceFrame calls, comparing the whole machine
     at every AdvanceFrame and every finished picture.
   - The ROM's code can overrun a frame (lag), and ported code never does. Differences within two AdvanceFrames
     of a lag are counted apart as "after lag".
   - The count that must be 0 is "with RAM/state differences" (and pictures "differ"). Use `--stop` to stop at
     the first difference and `--show K` to print more.
   - This is the test for routines that wait, and for the program as a whole.
3. Make power-on recordings for the parts of the game you port with `web/tests/engine/make_rec.mjs`, which takes
   a scripted pad. Put them in `out/port/` (gitignored), and say in your module which recording covers it.

Never commit the ROM or anything extracted from it (`rom/`, `gfx/`, `out/`, `web/gen/`,
`third_party/.../data|build`).
